# Amu を本家の最新版（Orchestration V2）に載せ直す計画

- 作成: 2026-10-07
- 作業ブランチ: `amu-v2`（`origin/main` 611132c17 から）。作業フォルダー `task/t3code-v2`
- 今の Amu（`amu` ブランチ、0.0.47）は触らない。使い続けながら作業する

## 目的

本家 T3 Code の 10/2 以降の作り直し（会話の途中で全 AI を乗り換え、AI どうしの作業の依頼、スマホまわり）を Amu に取り込む。Amu 独自の機能はすべて新しい土台に載せ直し、結パパの会話データを失わない。

## データの守り方（最優先）

1. 作業前のバックアップ: `~/Library/Application Support/Amu/backups/before-v2-20261007/`（state.sqlite は読み取り専用、33 スレッド・3,259 メッセージ、integrity ok）
2. 本家は初回起動時に `state.sqlite` を `statev2.sqlite` に写し、写しだけを移行する。元の `state.sqlite` は書き換えない（`initializeV2Database.ts`）。
3. **番号の衝突**: Amu 0.0.45〜0.0.47 は独自の移行を 55・56 番で記録済み。本家の移行は「記録済みの最大番号より大きいものだけ」実行するので、そのままでは本家の 55 番（V2 本体）が飛ばされる。→ `amuForkMigrations.ts` が、写しの台帳から Amu の 55・56 番の行（番号と名前が両方一致するものだけ）を消してから移行を流す。
4. 本家の取り込みは、ユーザーとアシスタントの発言だけを移す。ツールの実行記録・差分・承認・計画は新しい画面に出ない（元の DB には残る）。
5. 試験はすべて `env -i` で切り離した写しで行う。本物の Amu で新版を開くのは、更新の時だけ。

確認済み（2026-10-07 23:57）: バックアップの写しで本家サーバーを起動 → Amu の 55・56 番を消して 55〜58 番が流れた、33 スレッドすべて取り込み、元の DB の md5 は不変。

## 戻し方

- 新版で不具合があれば、更新の仕組みの自動の戻しが働く。手で戻す場合は GitHub の 0.0.47 を入れ直す。
- 0.0.47 は `state.sqlite` を読むので、新版で始めた会話（statev2.sqlite にだけある）は旧版には出ない。新版で作った会話を旧版に戻す手段はない。
